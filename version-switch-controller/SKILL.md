# 版本切换管理

## R — 原文 (Reading)

> 版本切换从含义上讲是一个新旧版本生产发货的衔接过程，行动上是由一个动作触发，从某一时刻起停止旧版本的采购计划同时开始启动新版本的采购计划。这样一个决定可能会带来以下后果：（1）新版本物料未齐套时旧物料既已消耗完，造成生产停顿，供货断档；（2）开始使用新版本后旧版本还有大量的物料未消耗完，成为呆死料。
>
> — 华为计划手册, 2.6.2 版本切换管理

> 在PV4/PV8系统的版本切换的过程中，"各产品线进度不同步、市场需求判断失误、老版本物料不够用、……"都打乱了切换部署。对版本切换，一定要建立以产品线为主体，涵盖各相关环节（中研、电信设计、计划、用服、跨产品线）的大项目管理模式；同时，在制订版本切换方案的初期，就要兼顾新老版本的兼容性，从源头降低切换的难度。
>
> — 华为计划手册, PV4/PV8版本切换案例

## I — 方法论骨架 (Interpretation)

版本切换管理是一个以物料控制为主线的跨部门协同流程。核心目标是：保障新版本按策略切入供应链，保障新老版本切换中的连续供货，防止老版本产生非政策性呆死料。

版本切换按需求分为五类：产品路标要求、市场需求变化、解决网上问题、降低成本、解决器件供应问题。每类对应不同策略（平滑/强行/权衡）。

控制主线覆盖五个环节：市场（要货计划/电信设计/定价）、研发（新版本开发/物料计划/切换预警）、采购（老物料储备/长单控制/新物料采购）、生产（老版本计划控制/呆死料处理）、用服（维修备件/网上扩容）。

关键成功要素：跨部门同步齐步走、明确责任人和责任部门、多监控点设计、统一信息平台、新老版本兼容性设计。

## A1 — 书中的应用 (Past Application)

### 案例 1: PV4/PV8系统版本切换（2000年）
- **问题**: 接入网产品线决定从01版本升级到02版本，9月份决定10月后所有签单采用新系统，预计11月下旬老版本停止发货
- **方法论的使用**: 
  - 初期切换顺利，但未落实跨产品线同步（FA16由传输行销部销售，传输人员未参加切换会议）
  - 监控点设置不全面，忽略了成套部门
  - 新老版本不兼容，局方和销售人员对稳定性不放心
- **结论**: 跨部门沟通缺失、监控点不全、基础数据不一致、兼容性不足是失败根因
- **结果**: 11月中旬老版本物料将在年底欠货，紧急追加计划后仍欠货长达1周

### 案例 2: SD525切换（成本驱动）
- **问题**: 传输SD525在市场竞争成本压力下需要切换
- **方法论的使用**: 将低成本方案作为备用的竞争方案，实施新老版本的平滑切换
- **结论**: 成本压力下的切换需要速度与风险的平衡
- **结果**: 成功实现成本降低目标

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 新产品即将量产，需要制定老版本物料的消耗计划和新版本的切入时间表
2. 关键器件停产，需要开发替代单板并管理新旧物料的衔接
3. 多个产品线共用同一模块，需要协调不同产品线的切换进度
4. 版本切换过程中出现老版本欠货或新版本呆死料，需要复盘和调整
5. 客户要求使用老版本扩容，但公司希望推广新版本，需要决策切换策略

### 语言信号 (用户的话里出现这些就应激活)

- "版本切换"
- "新老版本怎么衔接"
- "产品换代"
- "老物料还没用完新版本就上了"
- "切换断货了"
- "版本升级物料怎么处理"
- "平滑切换"

### 与相邻 skill 的区分

- 与 `inventory-health-diagnoser` 的区别: 本 skill 专门处理版本切换这一特定场景下的物料衔接和跨部门协同，而非通用库存诊断
- 与 `rd-logistics-planner` 的区别: 本 skill 聚焦版本切换执行过程，rd-logistics-planner 覆盖更广的研发物流全生命周期
- 与 `production-control-operator` 的区别: 本 skill 处理跨版本的物料计划衔接，production-control-operator 处理日常排产和发货

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **明确切换类型与范围**
   - 完成标准: 确定切换属于五类中的哪一类（产品路标/市场需求/解决问题/降低成本/器件供应），明确涉及的产品、模块、单板、结构件范围
   - 关键输入: 产品层次（整机/模块/单板/结构件）、切换原因文档

2. **评估新老版本兼容性**
   - 完成标准: 给出兼容性结论和影响评估
   - 检查项: 配套件是否通用、母板是否需要更改、局方备板备框投资保护、系统稳定性验证
   - 判停条件: 若不兼容且客户有强烈保留需求，建议采用"并存"策略而非强制切换

3. **制定切换策略（三选一）**
   - 完成标准: 根据切换类型选择并确定策略
   - 策略选项:
     - **平滑切换**: 老版本物料原则上消耗完再切（适用于产品路标要求）
     - **强行切换**: 快速响应，牺牲部分老版本库存（适用于解决网上问题）
     - **权衡切换**: 平衡需求与开发进度，作为竞争备用方案（适用于降低成本）

4. **建立跨部门大项目管理模式**
   - 完成标准: 明确五个环节的责任人和沟通机制
   - 五环节矩阵:
     | 环节 | 责任人/部门 | 关键交付 |
     |---|---|---|
     | 市场 | 行销计划/电信设计 | 要货计划、签单版本控制 |
     | 研发 | PDT/项目管理处 | 新版本开发进度、物料计划、切换预警 |
     | 采购 | 采购计划/CEG | 老物料储备、长单控制、新物料采购 |
     | 生产 | 生产计划/调度 | 老版本计划控制、呆死料处理 |
     | 用服 | 服务计划 | 维修备件、网上扩容需求 |

5. **设计监控点体系**
   - 完成标准: 在关键节点设置预警机制
   - 监控点示例:
     - 远期: 市场需求异常（成套部门）→ 触发改单
     - 中期: 电信设计切换通知落实 → 确认各产品线收到
     - 短期: 生产计划供货能力预警 → 触发增补计划
   - 判停条件: 任一监控点触发异常，立即启动应急预案

6. **确定呆死料控制目标并跟踪**
   - 完成标准: 根据切换策略和老物料库存及新版本退出进度，确定呆死料控制金额目标
   - 跟踪频率: 每周检查实际消耗 vs 计划消耗偏差

7. **输出版本切换方案文档**
   - 完成标准: 包含切换原因、范围、策略、责任矩阵、监控点、风险预案、呆死料控制目标

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯软件SaaS产品的功能迭代（无物理BOM和物料约束）
- 单一原材料的供应商切换（属于采购管理范畴，不需要五环节协同）
- 已完全停产多年的尾料清理（用 inventory-health-diagnoser 的死料处理即可）

### 作者在书中警告的失败模式

- 各产品线进度不同步：FA16案例中被传输行销部"忽略"的需求积少成多，直接推迟切换进程
- 监控点设置不全面：只在市场、生产计划设监控点，忽略了成套部门，导致预警失效
- 基础数据不准确：各信息平台不统一，录入时间不一致，市场需求数据一直不够准确
- 新老版本不兼容：局方从备板投资、稳定性、人员培训等因素出发拒绝新版本，导致切换成本增加

### 作者的盲点 / 时代局限

- 基于通信设备制造业的多层级BOM和较长生命周期特征；消费电子等快速迭代行业的切换节奏可能更快
- 案例中的版本切换以"停止老版本采购"为触发动作，现代模块化架构（如软件定义硬件）可能支持更灵活的灰度切换

### 容易混淆的邻近方法论

- ECO（工程更改单） vs 版本切换: ECO是BOM层面的工程更改，版本切换是产品层面的生产发货衔接；ECO可能触发版本切换，但二者管理粒度不同
- 停产器件处理 vs 版本切换: 停产器件处理是被动的替代方案，版本切换是主动的产品演进；但二者都需要储备和替代计划

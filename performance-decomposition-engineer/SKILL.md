# performance-decomposition-engineer

## When to Activate

- 用户提到"绩效分解"、"跨部门绩效"、"端到端绩效"
- 销售部门抱怨"产品不行"，研发抱怨"销售卖不动"，互相甩锅
- 绩效考核只看最终数字，没人对过程负责
- 想设计"全员为结果负责"的绩效体系
- 讨论"一个结果分解为一个体系多个环节"

## Core Philosophy

> "华为的绩效管理建立在对一个结果分解成无数个活动的基本上，这个活动可能在研产销环节，甚至在后勤体系，全部进行了分解，每个节点都承担着销售的责任，所以整个华为是一个营销型的组织。"

**传统误区**：
- 销售收入 = 销售部门的KPI
- 产品质量 = 质量部门的KPI
- 交付及时率 = 交付部门的KPI

**华为做法**：
- 销售收入是**整个公司的结果**，必须分解为研发、生产、交付、销售、后勤的共同活动
- 每个部门都承担部分责任，形成**过程责任制**

## The Decomposition Model

### 核心公式

```
最终结果 = Σ（跨部门关键活动 × 责任权重）
```

不是简单地把结果指标拆分给各部门，而是把**产生结果的过程**拆解为跨部门协作活动。

### 案例：销售收入的分

**传统做法**：
- 销售部：销售收入 100%
- 研发部：新产品数
- 生产部：产量
- 交付部：交付及时率

**华为做法**：销售收入由以下活动共同构成，每个活动都有责任主体：

| 活动环节 | 责任部门 | 考核权重 | 具体指标 |
|---|---|---|---|
| 客户关系维护 | 销售 | 15% | 客户拜访频次、高层互动 |
| 产品竞争力 | 研发 | 15% | 客户决策人参观后的认可度 |
| 方案匹配度 | 研发/销售 | 10% | 方案评审通过率 |
| 交付可靠性展示 | 交付/生产 | 15% | 客户参观生产线/交付现场评价 |
| 商务谈判 | 销售 | 15% | 合同条款、回款条件 |
| 交付实施 | 交付 | 15% | 交付周期、客户验收满意度 |
| 售后服务 | 服务 | 10% | 问题响应速度、客户满意度 |
| 财务支持 | 财务 | 5% | 开票及时性、信用支持 |

**关键洞察**：
- 研发人员也要考核"客户决策人对产品的认可度"——因为销售成功需要研发在客户面前证明产品规划
- 生产/交付人员也要考核"客户参观后的信任感"——因为客户买的不只是产品，更是长期服务承诺

### 更精细的分解示例

**销售人员的奖金计算**：
- 销售收入指标 ≤ 20%
- 其他过程指标占 80%：
  - 本月是否请到客户决策层参观公司（5%）
  - 新产品推介完成度（10%）
  - 交付团队对接及时性（10%）
  - 客户满意度调研（15%）
  - 回款率（20%）
  - 战略客户渗透率（10%）
  - 竞争对手信息反馈（10%）

## Decomposition Principles

### 原则1: 结果导向，过程分解
- 最终目标清晰（如：销售收入、客户满意度）
- 但考核的是**支撑结果的关键活动**，而非结果本身

### 原则2: 跨部门共担，而非割裂
- 同一项活动可能涉及多个部门，共同承担责任
- 避免"销售签单、交付背锅"的割裂

### 原则3: 按流程节点设指标
- 沿着端到端流程（如LTC、IPD）设置考核节点
- 每个节点都有明确的责任部门和验收标准

### 原则4: 数据可追溯
- 每个活动指标都有明确的数据来源
- 减少主观评价，增加客观记录

## Practical Playbook

### Step 1: 选定要分解的最终结果

选择一个对组织至关重要的最终结果，例如：
- 销售收入 / 合同额
- 客户满意度（NPS）
- 新产品上市成功率
- 项目交付利润率

### Step 2: 绘制端到端价值流

画出从"客户需求产生"到"客户满意付款"的完整流程：

```
客户需求 → 市场洞察 → 产品研发 → 生产制造 → 销售签约 → 交付实施 → 售后服务 → 客户复购
```

### Step 3: 识别每个流程节点的关键活动

对每个节点问三个问题：
1. 这个节点有哪些**关键活动**直接影响最终结果？
2. 这些活动由**哪些部门**参与？
3. 如何**衡量**这些活动做得好与不好？

### Step 4: 设定跨部门共担指标

**模板**：

| 流程节点 | 关键活动 | 责任部门 | 考核指标 | 权重 | 数据来源 |
|---|---|---|---|---|---|
| 示例 | 客户参观接待 | 研发+交付+销售 | 决策层参观后认可度≥4分 | 10% | 客户调研 |

**注意**：
- 权重之和不必等于100%，因为不同最终结果可以分别分解
- 同一部门可能在多个节点承担责任

### Step 5: 建立数据收集与复盘机制

- 每个指标必须有客观数据来源（系统记录、客户签字、第三方调研）
- 月度/季度复盘：哪些节点拖了后腿？是活动设计问题还是执行问题？
- 年度优化：根据业务变化调整活动分解

## Application Examples

### 场景A: 新产品上市成功

**最终结果**：新产品首年销售额达标

**分解活动**：
- 市场洞察：目标客户需求验证完成度（市场部）
- 产品定义：产品规格与客户需求匹配度（研发+市场）
- 研发质量：首批客户试用满意度（研发+服务）
- 生产准备：量产能力与交付承诺（生产+供应链）
- 销售培训：销售团队产品知识考试通过率（销售+研发）
- 上市推广：关键客户推介会覆盖率（市场+销售）
- 首批交付：首批订单交付周期（交付+生产）

### 场景B: 客户满意度提升

**最终结果**：年度NPS提升10分

**分解活动**：
- 销售阶段：承诺兑现率（销售）
- 研发阶段：需求变更响应速度（研发）
- 交付阶段：交付质量一次合格率（交付）
- 服务阶段：问题闭环时效（服务）
- 财务阶段：账单准确性与及时性（财务）
- 后勤阶段：客户接待与行政支持（行政）

## Anti-Patterns

- ❌ 把结果指标简单按比例拆给各部门（销售80%、研发10%...）——这不是分解，是摊派
- ❌ 活动指标过多过细，无法管理——每个最终结果分解为5-8个关键活动即可
- ❌ 数据来源不清楚，靠主观打分——分解必须建立在可追溯的数据上
- ❌ 只分解不复盘——分解是手段，持续改进才是目的
- ❌ 忽视部门间共担指标——只考核本部门独立产出，不考核协作产出

## STOP Checkpoints

- [ ] 最终结果是否是对组织最重要的1-3个目标？
- [ ] 每个关键活动是否都有明确的责任部门和可衡量的指标？
- [ ] 数据来源是否客观可追溯，而非主观评价？
- [ ] 跨部门共担指标是否占比足够（建议≥30%）？
- [ ] 是否建立了定期复盘和动态调整机制？

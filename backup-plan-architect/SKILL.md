# backup-plan-architect

## Metadata
- **Source**: 《华为管理手册（5版）——跨界管理》, 2023
- **Domain**: 供应链安全 / 极限生存 / 核心环节自主可控
- **Confidence**: high (海思芯片+鸿蒙OS多案例+美国制裁实战验证)
- **Revision**: 1.0

## When to Activate

当用户需要以下支持时激活：
- 评估关键供应链/技术/人员的"卡脖子"风险
- 设计核心环节的自主可控或备份方案
- 讨论"如果XX供应商断供/XX平台被封禁，我们怎么办"
- 制定极限生存预案（业务连续性计划）
- 评估"备胎转正"的时机和条件

不适用于：已有成熟替代方案的标准件采购、非核心业务的冗余设计、纯粹的心理安慰型备份。

## Core Methodology

### 备胎战略四层架构（4-Layer Backup Architecture）

#### Layer 1: 识别"战略旗帜"（Strategic Flag Identification）
不是所有环节都需要备胎。只有"战略旗帜"才值得长期备胎投入。

**判断标准**（满足任一即列为战略旗帜）：
1. **断供即瘫痪**：该环节被断供，主营业务立即停摆
2. **议价权丧失**：该环节被单一供应商控制，长期利润被侵蚀
3. **安全红线**：涉及数据安全、国家安全、核心知识产权
4. **代际锁定**：该环节决定下一代技术路线的选择权

**华为案例**：
- 海思芯片 = 战略旗帜（断供即瘫痪+代际锁定）
- 鸿蒙OS = 战略旗帜（断供即瘫痪+安全红线）
- 办公套件 = 非战略旗帜（可用WPS替代，切换成本低）

#### Layer 2: 备胎分级建设（Backup Grading）

| 级别 | 名称 | 特征 | 投入策略 | 华为案例 |
|------|------|------|---------|---------|
| S级 | 影子系统 | 与主系统并行运行，随时可切换 | 每年投入≥主系统维护成本的30% | 鸿蒙OS（安卓正常时保持迭代） |
| A级 | 热备能力 | 平时不用，但团队/技术持续储备 | 核心团队保持，定期演练 | 海思芯片（华为手机用高通时也自研） |
| B级 | 冷备方案 | 有替代方案设计，需要启动时间 | 文档化+关键人才储备 | 部分EDA工具替代方案 |
| C级 | 应急采购 | 市场上有替代供应商，可快速切换 | 供应商清单+合同模板 | 非核心元器件双源采购 |

#### Layer 3: "自己的狗食自己先吃"（Dogfooding Principle）

任正非原则："自己生产的降落伞自己先跳。"

备胎不能只是"实验室产物"，必须在真实业务场景中持续运行：
- 海思K3V2性能极差，但任正非坚持华为旗舰机必须搭载——"如果没有华为手机，海思芯片就无法成长"
- 鸿蒙微内核在安卓手机上以TEE形式运行，处理人脸支付等高安全场景
- 华为云在对外服务前，先支撑华为自身全球业务上云

**自检三问**：
1. 你的备胎产品有没有在真实业务场景中运行？
2. 你的备胎团队有没有承受过真实的交付压力？
3. 你的备胎方案有没有经历过真实的故障切换演练？

#### Layer 4: 备胎转正触发机制（Activation Trigger）

备胎不是越多越好，需要设计明确的"转正触发条件"：

**华为鸿蒙转正触发条件**：
- 触发条件：安卓系统无法使用（美国禁令）
- 切换时间："一夜之间"（1-2天）
- 切换范围：从IoT设备优先→中低端手机试水→主力机型
- 切换策略：兼容层+原生层并行，确保生态不中断

**通用转正触发条件设计**：
```
触发条件 = 具体事件（如"某供应商停止供货"）
           + 持续时间（如"超过30天无法恢复"）
           + 影响范围（如"影响核心业务>20%"）
```

### 极限生存信号释放（Survival Signal Emission）

备胎的价值不仅在于"用"，还在于"威慑"。

**华为实践**：
- 鸿蒙OS发布时高调宣示"随时可以用于手机"——不是真的要换，而是让对手知道"断供安卓≠杀死华为"
- 海思芯片的存在让高通在定价时有所顾忌
- 效果："华为手机有换成鸿蒙的能力，美国人会对禁华为感觉很异样，决策难度急剧上升"

**适用边界**：
- 需要备胎本身确实可用（不能是空城计）
- 需要有一定市场影响力（小企业释放信号无效）
- 需要与"市场逻辑"平衡（不能为了威慑而牺牲商业利益）

## Usage Flow

1. 用户描述业务依赖的关键外部环节 → Layer 1识别战略旗帜
2. 用户确认需要备胎的环节 → Layer 2确定备胎级别
3. 用户提出备胎建设方案 → Layer 3检验"狗食自吃"原则
4. 用户询问何时启用备胎 → Layer 4设计转正触发机制

## Example

**Input**: "我们的SaaS产品重度依赖AWS，如果中美关系恶化AWS被限制，我们该怎么办？"

**Skill Response**:
> **Layer 1 战略旗帜识别**：
> AWS依赖是否=战略旗帜？判断：
> - 断供即瘫痪？是的，如果AWS账号被封，服务直接不可用
> - 但切换成本？中等（容器化部署可迁移）
> - 结论：属于战略旗帜，但需要区分"热备"vs"冷备"
>
> **Layer 2 备胎分级**：
> 建议SaaS企业的云备胎策略：
> - A级热备：核心服务同时在阿里云/腾讯云部署，流量按比例分配（如80% AWS + 20% 国内云）
> - 理由：云服务的备胎不能是"冷备"——冷启动时数据同步、性能调优、DNS切换需要数周
> - 成本：增加约20-30%基础设施成本，但换来随时可切换的能力
>
> **Layer 3 狗食自吃**：
> 你的研发团队日常是否在国内云上跑CI/CD？是否用国内云做staging环境？
> 如果答案都是"No"，那么所谓的"备胎"只是PPT上的备份方案。
> 建议：立即将至少一条非核心产品线完整迁移到国内云，让团队"先跳降落伞"。
>
> **Layer 4 转正触发**：
> 设计明确的触发条件：
> - 触发1：AWS服务可用性<99%持续>72小时
> - 触发2：收到AWS账号限制通知
> - 触发3：监管机构明确要求数据不得出境
> - 切换动作：DNS切流（分钟级）→ 数据同步验证（小时级）→ 全量迁移（天级）

## Anti-Patterns
- ❌ "备胎就是备用供应商名单" — 没有真实运行过的备胎=没有备胎
- ❌ "备胎建好了但不敢用" — 不敢吃自己的狗食，备胎永远不成熟
- ❌ "为了备胎而备胎" — 非战略环节不需要备胎，避免资源浪费
- ❌ "备胎转正=全面替代" — 华为鸿蒙的思路是"能用安卓就用安卓，不能用了再用鸿蒙"，而非全面替代

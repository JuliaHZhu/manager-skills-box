# rd-performance-designer

研发体系绩效管理：通过「效益指标+效率指标+路径指标+行为指标」四维指标体系，解决研发人员考核难、衡量难、激励难的问题，构建适合研发特点的绩效管理体系。

## 触发条件

当用户需要设计研发人员绩效考核、讨论研发部门如何考核、IPD体系下的研发绩效、项目制研发考核、或研发指标如何提炼时激活。

**关键词**：研发绩效 / 研发考核 / IPD绩效 / 研发指标 / 项目考核 / 研发人员绩效 / R&D绩效管理 / 技术团队考核

## 使用说明

### 第一步：研发考核的四大难点

**1. 绩效指标提取困难**：
- 研发工作独特性高，工作成果不易衡量
- 难以提炼直观量化的数字性指标
- 代码行数等量化指标容易误导（员工把简单命令拆成多个命令）

**2. 工作内容界定困难**：
- 预研人员的成果可能只是证明某种方法可行与否
- 证实与证伪具有同样的价值
- 任务下达前难以明确界定

**3. 定性内容较多**：
- 影响考核的公正性
- 主管和员工对"做得好"的标准理解不一致

**4. 考核方式选取问题**：
- 很多研发管理者回避考核难题
- 采取背后打分、不沟通的方式
- 导致考核流于形式

**STOP检查点**：
- [ ] 是否避免了简单量化指标（如代码行数）的陷阱？
- [ ] 是否区分了预研、开发、维护等不同研发阶段的考核重点？
- [ ] 考核方式是否透明、可沟通？

### 第二步：四维指标体系设计

**核心逻辑**："正确的行为，沿着正确的道路，达成正确的结果"

**1. 效益指标（市场价值）**：
- 衡量研发成果在市场中产生的价值
- 指标示例：产品销售额、市场占有率、客户满意度、产品故障率
- **注意**：效益指标具有滞后性，不适用于个人考核，适合部门/团队/项目考核
- 考核周期：按项目周期进行

**2. 效率指标（内部效能）**：
- 衡量公司内部的研发效率和阶段成果
- 分为路径指标和行为指标

**3. 路径指标（过程检测）**：
- 衡量研发过程是否符合总体研发规划
- 指标示例：
  - 产品开发周期
  - 研发费用
  - 产品规划符合度 = 1 - M/(T+M)×70% - N/(T+M)×30%
    - T: 应启动的版本数
    - M: 非正常增减版本数
    - N: 未按路标执行的版本数
  - 批次整改率
  - 单板/整机直通率
  - 产品数据准确率
- 考核周期：按固定时间段（季度）
- 权重：占整体考核的50%-70%

**4. 行为指标（职业行为）**：
- 衡量研发过程中的正确职业行为
- 指标示例：
  - 文档完整率
  - 项目报告完整性
  - 数据差错率
  - 知识共享参与度
  - 代码审查通过率
  - 技术评审参与度
- 来源：可从研发人员职业发展路径标准中提炼

**STOP检查点**：
- [ ] 指标体系是否覆盖了效益、效率、路径、行为四个维度？
- [ ] 效益指标是否只用于团队/部门考核，不用于个人考核？
- [ ] 路径指标和行为指标是否用于个人考核，权重是否合理？

### 第三步：部门团队考核 vs 员工个人考核

**部门/团队考核**：
- **侧重**：效益指标 + 路径指标
- **周期**：
  - 效益指标：按项目周期考核（项目结束后一段时间）
  - 路径指标：按季度考核
- **权重**：路径指标占50%-70%，体现业绩导向和市场导向
- **奖金分配**：需配合考核周期设计中期激励方案

**员工个人考核**：
- **侧重**：行为指标 + 路径指标
- **方式**：PBC（Personal Business Commitment）
- **周期**：季度
- **内容**：
  - WIN（赢的承诺）：行为指标和路径指标的结合
  - EXECUTE（执行承诺）：达成目标的方法、策略、工具
  - TEAM（团队承诺）：与团队成员的协作配合

**PBC在研发中的示例**：

| PBC维度 | 不恰当的PBC | 恰当的PBC |
|---------|------------|----------|
| WIN | 提高客户满意度 | 通过收集客户群体反馈，提高客户满意度10% |
| EXECUTE | 准备客户分析材料 | 依据解决客户投诉行动计划，十天内解决相关投诉 |
| TEAM | 解决如何评价客户满意度的问题 | 建立跨部门合作小组，每季度末交流沟通跟踪 |

**STOP检查点**：
- [ ] 部门考核和个人考核的侧重点是否区分开？
- [ ] 个人PBC是否采用了WIN/EXECUTE/TEAM三层结构？
- [ ] 团队考核的奖金分配是否与个人价值回报挂钩？

### 第四步：研发考核的分层分类设计

**高层研发管理者**：
- 年度考核
- 关注中长期技术战略、技术路线选择、重大项目突破
- 述职+KPI，加入战略分解要求

**中层研发管理者（项目经理/技术经理）**：
- 半年度+年度考核
- PBC管理
- 关注项目交付、团队建设、技术规划

**基层研发人员**：
- 季度考核
- 要素考核表：调试了多少单板、多少主机、质量怎么样、有多少漏测、有没有大事故
- 及时激励、及时评价

**预研人员特殊考核**：
- 考核周期适度拉长
- 允许"证伪"作为有效成果
- 评价标准需前置明确

**STOP检查点**：
- [ ] 是否根据研发层级设计了不同的考核周期和方式？
- [ ] 预研人员是否有允许"证伪"为成果的评价机制？
- [ ] 基层研发人员是否采用要素考核而非复杂PBC？

### 第五步：基于IPD的研发绩效管理

**IPD体系下的绩效要点**：
1. **阶段评审点考核**：在每个TR（技术评审）点和DCP（决策检查点）设置考核
2. **跨部门团队考核**：PDT（产品开发团队）作为整体考核单元
3. **管道管理**：考核项目资源利用率、项目进度符合度
4. **结构化流程**：按照IPD阶段（概念→计划→开发→验证→发布→生命周期）设置里程碑考核

**关键指标**：
- 概念决策评审通过率
- 计划决策评审符合度
- 市场发布准时率
- 产品投资回报率
- 客户问题及时解决率

**STOP检查点**：
- [ ] 研发考核是否与IPD阶段评审点对接？
- [ ] PDT团队是否作为整体考核单元？
- [ ] 是否设置了管道管理和资源利用率指标？

## 反模式警告

⚠️ **以下做法会导致研发考核失效**：
1. 以代码行数作为重要考核指标（导致代码冗余、效率低下）
2. 只考核短期产出，忽视长期技术积累
3. 对预研人员要求明确的短期产出（忽视证伪价值）
4. 效益指标直接用于个人考核（忽视团队合作）
5. 考核方式不透明，背后打分不沟通
6. 所有研发人员用同一套考核模板，不分层级不分类型

## 研发绩效指标速查表

| 维度 | 指标类型 | 示例指标 | 适用对象 |
|------|----------|----------|----------|
| 效益 | 市场价值 | 产品销售额、市场占有率、客户满意度 | 部门/团队/项目 |
| 效率-路径 | 过程检测 | 开发周期、研发费用、规划符合度、直通率 | 部门/个人 |
| 效率-行为 | 职业行为 | 文档完整率、数据准确率、知识共享度 | 个人 |
| 效率-路径 | 质量指标 | 批次整改率、故障率、缺陷密度 | 团队/个人 |

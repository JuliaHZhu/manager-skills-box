# routine-exception-delegator — 例行与例外管理分离设计师

## R (Reading) — 原文引用

> "对于流程已经十分清晰的系统，可以由秘书直接来完成；经理主要管理例外的系统，以及例行管理中一些界限很模糊的、判断不是比较清楚的、决策量比较大的系统。这就是现代管理中经理与秘书相互之间的关系。"（Ch25.1）

> "什么都管的经理是一个效率不高的秘书，什么决策都不做的秘书很难晋升为行政助理。"（Ch25.1）

> "秘书如果不主动参与决策，对例行问题中需要而且可以进行管理的工作，还是被动接受领导的命令，那她以后也很难晋升为经理。因此秘书是初级的管理人员，不能将分工绝对化，否则就不会使企业高效。"（Ch25.1）

> "80%-90%的例行工作是由秘书进行管理，秘书有处理例行问题的权力。"（Ch26.1）

> "因为分工绝对化是以人治为基础的，而我们要建立以制度为基础的管理体系，谁明白制度，而又能承担责任，就应该得到授权去管理，因此一些例行的工作是可以由秘书来完成的，秘书是通向经理的第一步台阶。"（Ch25.1）

> "秘书的规范化服务是公司高速发展最重要的润滑剂。规范化服务重要的就是减少因格式不同、理解不同所带来的不增值的劳动。"（Ch25.2）

> "企业在IT管理中，秘书群是最重要的服务平台，没有他们的规范化的服务，企业就不可高速运转。"（Ch25.2）

## I (Interpretation) — 方法论骨架

**例行与例外分离**是现代管理中最简单但最难落地的原则之一。其核心逻辑：

```
管理者的时间分配
├── 例行工作（80-90%）→ 标准化 → 授权给支持人员/系统
│   ├── 特征：重复发生、规则清晰、不需要特殊判断
│   ├── 价值：维持组织正常运转
│   └── 风险：消耗管理者大量时间，使其无暇顾及战略
└── 例外工作（10-20%）→ 保留给管理者
    ├── 特征：首次发生、规则模糊、需要判断和决策
    ├── 价值：决定组织方向和突破
    └── 风险：如果管理者被例行工作淹没，例外工作也被草率处理
```

华为秘书体系的价值定位不是"打杂"，而是**组织例程的守护者和管理者**——她们通过规范化服务，让管理者从重复性事务中解放出来，专注于真正的例外决策。

**三个关键洞察**：
1. **秘书不是被动接收命令，而是主动管理例行**——她们对例行问题有管理权，不是简单的执行权
2. **分工不能绝对化**——经理也需要了解例行，秘书也需要参与部分决策，否则两者都无法成长
3. **规范化是润滑剂**——减少因格式不同、理解不同带来的不增值劳动

## A (Application) — 执行步骤

### 步骤1：识别例行 vs 例外

对管理者或一个岗位的工作内容进行全面梳理，用以下标准分类：

| 判定维度 | 例行（Routine） | 例外（Exception） |
|---------|----------------|------------------|
| 发生频率 | 周期性/高频发生 | 偶发/首次发生 |
| 规则清晰度 | 有明确SOP或制度 | 无现成规则或规则模糊 |
| 判断复杂度 | 按规则即可判断 | 需要经验、直觉和权衡 |
| 决策影响范围 | 局部/可逆 | 全局/不可逆或高成本 |
| 信息完整度 | 信息充分 | 信息不完整或不确定 |

**工具：工作日志分析法**
让目标管理者连续记录两周工作日志，逐条标注每条工作的类型和耗时，然后统计：
- 例行工作占比是多少？
- 哪些例行工作占用了最多时间？
- 哪些例外工作因为时间不够而被草率处理？

**STOP检查点1**：如果例行工作占比低于50%，说明该岗位要么已经高度优化，要么记录不完整（很多"随手处理"的例行工作被忽略了）。

### 步骤2：将例行工作标准化

对识别出的例行工作，按以下优先级进行标准化：

```
标准化优先级矩阵
            高频率
               │
    优先标准化 │ 优先标准化
    （快速见效）│ （核心痛点）
               │
低复杂度 ──────┼────────── 高复杂度
               │
    延后标准化 │ 谨慎标准化
    （价值有限）│ （需要精心设计）
               │
            低频率
```

**标准化输出物**（按复杂度选择）：
- **极简版**：Checklist（检查清单）
- **标准版**：SOP（标准操作流程，含步骤、责任人、时限）
- **完整版**：制度文件 + SOP + 模板 + FAQ

**STOP检查点2**：如果一条"例行工作"无法写出SOP（因为每次做法都不一样），说明它实际上是例外工作，只是被误认为例行。

### 步骤3：设计授权机制

将标准化后的例行工作授权给支持人员或系统：

| 授权对象 | 适用场景 | 关键设计 |
|---------|---------|---------|
| 行政秘书/助理 | 高频、低复杂度、需要人际沟通 | 明确授权边界、建立汇报机制、保留抽查权 |
| IT系统/自动化 | 规则极其清晰、无例外空间 | 设计异常处理路径，系统无法处理时自动升级 |
| 共享服务中心 | 跨部门共性事务 | 建立SLA（服务等级协议），明确交付标准和时效 |
| 外包/慧通模式 | 非核心、成本高或难招聘 | 明确质量标准和退出机制 |

**授权边界设计原则**：
1. **授权不授责**：支持人员执行，管理者仍对结果负责（通过抽查和复盘）
2. **例外升级机制**：明确规定什么情况下必须上报，避免支持人员越权或不敢决策
3. **双向反馈通道**：支持人员发现规则不合理时，有渠道提出优化建议

### 步骤4：管理者的例外工作聚焦

管理者从例行工作中解放后，应将时间重新分配到：

```
管理者时间再分配
├── 例外决策（原10-20% → 保持或增加）
│   ├── 战略方向判断
│   ├── 重大人事决策
│   ├── 跨部门资源协调
│   └── 危机处理
├── 规则优化（新增）
│   └── 把新出现的例外转化为新的例行规则
├── 人员培养（新增）
│   └── 培养支持人员处理更复杂的例行工作
└── 关系建设（新增）
    └── 客户、合作伙伴、关键人才的关系维护
```

**关键循环**：
```
例外发生 → 管理者处理 → 总结经验 → 转化为规则 → 授权给支持人员 → 管理者聚焦新例外
```

### 步骤5：建立秘书/支持人员的成长通道

**STOP检查点3**：如果只授权不培养，支持人员永远停留在执行层，管理者也无法真正解脱。

华为秘书的成长通道设计：
- **初级阶段**：执行标准化例行（一段到四段）
- **中级阶段**：优化例行流程、处理轻微例外（五段到七段）
- **高级阶段**：将例外转化为规则、培养新人、参与决策辅助（八段到九段）

**晋升标准**：能承担更复杂的例行 + 能处理更多类型的轻微例外。

## ⚠️ Anti-Example 黑名单

- ❌ 把"所有杂事都丢给秘书"当成例行与例外分离（这是分工不均，不是管理优化）
- ❌ 授权后完全不管、不复盘、不抽查（授权不等于放任）
- ❌ 把需要判断的工作强行写成SOP（SOP只适用于真正例行的场景）
- ❌ 管理者从例行中解放后去管更多例行（说明没有真正理解例外工作的价值）
- ❌ 忽视支持人员的成长通道，导致高流失率（人走了，积累的例程知识也丢了）

## 📋 Failure-Mode Fallback

| 如果用户... | 则... |
|------------|-------|
| 管理者不愿意放权 | 从小事开始，先授权1-2项低风险的例行工作，用结果建立信任 |
| 支持人员不敢接权 | 明确授权边界和升级机制，告诉他们"什么情况必须问我，其他情况你自己决定" |
| 授权后质量下降 | 检查是标准不清晰（优化SOP）还是执行不到位（加强培训和抽查） |
| 例行工作标准化成本太高 | 优先标准化高频+低复杂度的，不要试图一次性标准化所有事情 |
| 组织太小，没有专职支持人员 | 用"虚拟助理"模式，让团队中最擅长流程的人兼职管理例程，或借助工具自动化 |

## T (Test) — 验证问题

- 你的管理者每天有多少时间花在"这件事我上周已经处理过很多次"的工作上？
- 你组织中有多少"例外"实际上是因为没有规则造成的假性例外？
- 如果你最得力的支持人员明天离职，她管理的例行工作有多少是别人可以按文档接手的？
- 你的管理者最近一次深入思考战略问题是什么时候？如果记不起来，说明他被例行工作淹没了。

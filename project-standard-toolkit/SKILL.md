# 华为项目管理标准工具箱

## R — 原文 (Reading)

> 目前华为采用的通信工程项目管理方法使用的是“六步一法”包括：1)明确目标范围确认，2)项目重大里程碑确认，3)项目活动分解(WBS)准备工作计划，4)质量控制、实施指导书，5)进度计划和站点计划的修订，6)制定区域计划流程，一法就是项目的沟通策略。
>
> — 华为管理手册（项目管理）, Ch21

> 项目管理其实是有一些常用的工具和模板的……甘特图、燃尽图、WBS分解图、HOQ质量屋图、RACI图、矩阵组织图、PERT图、思维导图、决策树分析图、状态表。
>
> — 华为管理手册（项目管理）, Ch24

## I — 方法论骨架 (Interpretation)

华为将项目管理经验固化为**十大模板 + 六步一法 + 十张图表**，让项目经理“站在巨人肩膀上”，降低项目不确定性风险。

**十大模板（贯穿项目全周期）：**
1. **项目组成员表**：明确项目赞助人、项目经理、核心/非核心成员、职责、投入频度、主管经理
2. **项目策划/任务书**：项目背景与目的、目标（SMART）、里程碑计划、评价标准、假定与约束、干系人
3. **项目WBS表**：工作分解结构，任务名称→包含活动→工时估算→人力资源→费用估算→工期→RACI责任矩阵
4. **项目进度计划表**：甘特图形式，按周/日排列，关键里程碑、责任人
5. **项目风险管理表**：风险描述、发生概率、影响程度、风险等级（高/中/低）、响应计划、责任人、开放/关闭状态
6. **项目沟通计划表**：利益干系人→所需信息→频率→方法→责任人
7. **项目会议纪要**：会议目标、参加人员、发放材料、发言记录、会议决议、发放范围
8. **项目状态报告表**：当前任务状态、本周期主要活动、下周期计划、财务状况、上期遗留问题、本期问题与求助
9. **项目变更管理表**：变更描述、影响分析（成本/进度/资源）、变更程度分类、审批结果
10. **项目总结表**：时间总结、成本总结、交付结果总结、经验教训

**六步一法（通信工程项目管理方法）：**
1. 明确目标范围确认
2. 项目重大里程碑确认
3. 项目活动分解(WBS)准备工作计划
4. 质量控制、实施指导书
5. 进度计划和站点计划的修订
6. 制定区域计划流程
**一法**：项目的沟通策略

**十张常用图表：**
- 甘特图（进度可视化）
- 燃尽图（敏捷剩余工作）
- WBS分解图（层级化工作包）
- HOQ质量屋图（客户需求与技术特性关联）
- RACI图（职责矩阵：Responsible/Accountable/Consulted/Informed）
- 矩阵组织图（职能×项目的双重汇报）
- PERT图（关键路径与工期估算）
- 思维导图（项目全貌发散梳理）
- 决策树分析图（多方案选择）
- 状态表（多项目跟踪）

## A1 — 书中案例 (Application in Book)

**T客户考察公司项目**（贯穿十大模板示例）：
- 项目策划书：明确背景（A国战略市场、客户质疑供货能力）、目的（重建信心）、目标（7月31日前邀请CTO考察，预算20万）、评价标准（CTO在列、无内容失误、客户正面反馈、费用不超预算）
- WBS表：分解为“邀请客户→落实资源→预定后勤→实施考察→后续跟踪”5大工作包，每项细化到具体活动、工时、责任人、RACI
- 风险管理表：识别5大风险（客户无考察意愿、高层临时有事、样板点关闭、座谈效果不佳、后勤失误），分别制定响应计划
- 变更管理表：客户临时希望在香港停留一天，分析对成本（+5万）、进度（延迟1天）、资源（需香港接待人员）的影响，审批同意
- 项目总结表：时间、成本、交付结果差异分析，经验教训（前期需求分析应更准确，客户经理未重视客户委婉提出的购物愿望）

## A2 — 未来触发场景 (Future Trigger)

用户在以下情境会需要这个 skill：
- “项目总是做到哪算哪，没有统一的文档和标准”
- “新人项目经理不知道怎么写项目计划、怎么做WBS”
- “项目变更混乱，客户一句话就改，没有变更控制”
- “多个项目并行，老板要看状态报告，每次都要重新编”
- “项目结束了，知识经验没有沉淀，下次还犯同样的错”
- “需要一套拿来就能用的项目管理模板”

## E — 执行步骤 (Execution)

### Step 1: 建立十大模板基线（项目级）
为团队建立统一的模板库，每个新项目启动时强制使用：
1. 项目启动 → 填写《项目策划/任务书》+《项目组成员表》
2. 项目规划 → 输出《WBS表》+《进度计划表》+《风险管理表》+《沟通计划表》
3. 项目执行 → 产出《会议纪要》（每次关键会议）+《项目状态报告》（按周/双周）
4. 项目变更 → 任何范围/进度/成本变更必须走《变更管理表》
5. 项目收尾 → 提交《项目总结表》，经验教训入组织资产库

### Step 2: 推行六步一法（交付/工程类项目）
| 步骤 | 关键动作 | 输出物 |
|------|----------|--------|
| 1. 明确目标范围 | 与客户确认需求边界、验收标准 | 范围说明书 |
| 2. 重大里程碑确认 | 锁定不可妥协的时间节点 | 里程碑计划 |
| 3. WBS分解 | 按交付物分解到可分配工作包 | WBS表+准备工作计划 |
| 4. 质量控制 | 制定实施指导书、检查标准 | 质量计划+指导书 |
| 5. 进度计划修订 | 结合资源与风险，排定详细进度 | 甘特图+站点计划 |
| 6. 区域计划流程 | 多区域/多站点协同规则 | 区域协同计划 |
| 一法：沟通策略 | 明确沟通对象、频率、渠道 | 沟通计划表 |

### Step 3: 活用十张图表
根据项目类型和阶段选择工具：
- **启动期**：思维导图（全貌）+ WBS分解图
- **规划期**：甘特图（进度）+ RACI图（分工）+ PERT图（关键路径）+ HOQ（如有质量设计需求）
- **执行期**：燃尽图（敏捷团队）+ 状态表（多项目跟踪）+ 决策树（重大方案选择）
- **监控期**：甘特图（进度对比）+ 风险矩阵（风险状态）

### Step 4: 模板裁剪与适配
- **小项目**：可裁剪为“策划书+WBS+状态报告+总结”四件套
- **大项目**：十大模板全套+六步一法严格执行
- **研发项目**：增加PQA过程审计检查点、技术评审记录
- **销售项目**：增加LTC阶段 gate 检查表

## B — 边界与反例 (Boundary)

**不适用场景：**
- 纯探索性研究项目（如基础科学预研），目标不确定，无法做详细WBS和甘特图
- 创意/设计类项目，迭代方向随时变化，过度模板化会扼杀创造力
- 团队规模极小（1-2人），模板管理成本高于收益
- 已有成熟DevOps/敏捷工具链（如Jira+Confluence+GitLab）且团队习惯良好，无需额外纸质模板

**常见陷阱：**
- 为了填模板而填模板：模板是工具，不是目的；填写后束之高阁等于浪费
- 变更管理流于形式：表面有变更表，实际客户一句话就改，不分析影响
- WBS分解过细或过粗：过细导致管理成本爆炸，过粗导致失控；一般以“可分配给一个人、可在一周内完成”为度
- 忽视沟通策略：六步一法中“一法”是沟通，但往往被忽略，导致信息断层
